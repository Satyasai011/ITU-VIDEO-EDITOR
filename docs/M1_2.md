# M1.2 — Prism Interface Refinement

Version `0.1.2-m1.2`, versionCode **3**, applicationId **com.itu.videoeditor**. M1.2 only; no M2A or M2B functionality.

## Completed functionality

- A more compact Crystal Aurora dashboard with real cached project thumbnails. Dashboard explicitly counts projects and imported source videos separately.
- Media Vault now reads independently persisted source records, including imported videos that have no project yet. Grid/List mode persists in the original DataStore preference; search, sort, filters, metadata dialogs and source/project actions are real. Counts show filtered/total imported videos plus project count. Reusing a URI does not invent another physical video. Multiple projects can reference one source. Failed imports are reported, not silently counted.
- MediaExtractor/MediaMetadataRetriever inspection runs in the background. Resolution, rotation/orientation, source video codec, video bitrate when reported, container bitrate when reported, duration, provider/file size, and audio stream codec/sample rate/channels/bitrate/language are retained. Missing properties display **Unknown**. No 4K or 60 FPS source labels are inferred from presets.
- Frame rate uses presentation timestamps from up to 360 frames where available, preserving fractional rates such as 60000/1001 (59.94 FPS). It tolerates reordered timestamps and timestamp quantization; detected cadence variation is explicitly described as a sample, not a guarantee about the entire file. If timing cannot be sampled, reported source metadata is used and labelled; otherwise FPS is Unknown.
- Prism Project Setup inspects all picker-returned videos and lists failures. The first selected video's display dimensions and observed/reported rate propose project intent. If the first video cannot be read, another source is not silently substituted. Every readable imported source remains in Vault, even if setup is cancelled. The confirmation screen flags resolution/rate mismatches and sampled variable timing, allows explicit format edits/Unknown fields, and offers the last confirmed format only through an explicit button. Source metadata is never overwritten by that suggestion. Only the first selected source is edited in a project; extra videos are not a fake multitrack composition.
- Project format is persisted separately from original source dimensions. It does not enable resolution/FPS conversion. The actual export remains the original 720p H.264/AAC foreground validation path.
- The Obsidian Precision editor retains fitted video preview, timecodes, transport/trim controls, compact contextual phone panels and collapsible tablet panels. Source information now shows real inspection data, with Refresh metadata. Preview looping, guidance and initial panel layout obey saved preferences.
- Settings has Video & Playback, Export & Quality, Editing Preferences, Appearance, Workspace Layouts and Storage & Performance sections. Implemented controls include preview mute/loop, trim guidance, reduced motion, initial tablet-panel collapse, Vault Grid/List default, hardware encoder inspection, and cache usage/clearing. Future export presets, named workspace layouts, undo and operation journals are text explanations, not inert controls.
- Outlined 24dp Prism glyphs, 48dp minimum targets, 56dp primary controls, subtle cyan selection, restrained violet accents and system-aware motion are preserved.

## Data preservation

Room schema migrates **1 → 2** by adding a nullable project-format field and a separate media_sources table. Existing project IDs, source URIs, names, original metadata, saved trim bounds and timestamps are retained. No destructive migration is configured. Old projects are backfilled into the source registry, with Unknown values for properties never inspected; unreadable sources report the inspection failure. Creation commits source/project rows transactionally; trimming keeps the original atomic update. DataStore file name and existing preference keys are unchanged.

The prior app did not have a full autosave journal or recovery snapshots. Existing creation/explicit Save trim persistence remains; M1.2 does not pretend to add M6 autosave/recovery functionality. Setup drafts survive configuration changes but an unconfirmed draft is not a recovery snapshot. Already imported sources remain in Vault if the process dies before project confirmation.

Real thumbnails still use bounded background generation/caches. Cache clearing deletes only disposable thumbnails. Source media and exported videos are never modified or deleted by these operations.

## Signing status — read before installing

The delivered M1.1 APK's certificate SHA-256 is:

`9887fa28c21cc5684780c445b257ec312c6c09e0fe0e8684a66a27df4fdbdee8`

The retained local debug private key has certificate:

`50832023b0fe979d8a5c08c235b2ae9380e1c4612b99f94667ace92d1586d320`

They **do not match**. The M1.1 GitHub runner's private key was not saved in the project or uploaded as an artifact. A private signing key cannot be recovered from an APK or a certificate fingerprint. No physical device is attached, so installed device contents have not been inspected. The user identified the installed APK as the delivered M1.1 Drive/GitHub build; comparison is against that verified artifact, not an ADB read of the device.

The GitHub connector has no signing-secret operation, and the CLI returned **403 Resource not accessible by integration** when requesting the repository's Actions encryption key. No secret was created or changed. Private key material is never committed, logged, uploaded as an artifact or put in the Gradle cache.

The workflow supports an **ITU_DEBUG_KEYSTORE_BASE64** repository secret containing the original debug keystore (standard Android debug alias/password). If supplied, the resulting APK must match the checked-in M1.1 certificate or publication fails. This is a certificate check, not a claim of a tested device update. Until the matching key is restored, artifacts are explicitly labelled **fresh-install-only** and include SIGNING_STATUS.json. These are clean test-device APKs, **not M1.1 updates**. The application ID is not changed to evade signature checks.

**Protect existing projects: do not uninstall or clear the current M1.1 app to resolve this conflict.** No existing app/device data was changed during development. A differently signed APK cannot update that installation. Use a separate clean Android test device/emulator for an incompatible build, or wait for the original signing key. Merely changing the version code does not fix signature incompatibility. Original source files would remain after uninstall, but project state/preferences would not; uninstall is not a data-preserving installation procedure.

If the original keystore is available outside this workspace, add it through GitHub repository Settings → Secrets and variables → Actions, never in chat or a Git commit. Rerun Android Debug APK. Certificate verification must pass before attempting a normal update; physical update/migration still needs validation. No matching private key is currently available to configure this automatically.

## Verification and limitations

Local verification completed on 2026-11-08 with JDK 17, Gradle 8.9, Android SDK/Build Tools 35:

- Debug APK and instrumentation APK compiled successfully.
- **21 unit tests passed**, no failures/errors.
- Android lint: **0 errors, 14 dependency-update warnings**.
- The actual migration SQL was executed in an in-memory SQLite database seeded with a v1 project: source URI, name, metadata, saved trim and timestamps were preserved; columns match the exported Room v2 schema. This is separate from the Android Room emulator test.
- FFprobe verified the real 59.94-FPS H.264/AAC test fixture.
- APK identity/signature verified; local certificate does **not** match the delivered M1.1 certificate. Installed device was not inspected.
- The original ValidationExporter and TrimRange model were compared with the M1 source archive and remain unchanged. Source trimming's atomic SQL update remains intact.

Evidence: [build log](validation/m12-local-build.log), [lint](validation/m12-lint.txt), [media unit tests](validation/m12-TEST-com.itu.videoeditor.MediaInfoTest.xml), [signing](validation/m12-local-signing.json), [fixture inspection](validation/m12-fixture-ffprobe.json).

See the accompanying m12 validation reports for local build, unit, lint, signing and fixture evidence. The local environment has no connected Android device and no KVM device. GitHub Actions adds a separate API 35 x86_64 emulator test job for actual navigation, real 59.94-FPS MP4 inspection/audio/size/codec checks, preference persistence, saved trim and version-1 database migration. Its completed run/reports are the authority for emulator results; this document does not pre-claim that pending CI job passed.

The generated instrumentation fixture is a real 320×180 H.264/AAC MP4, 60000/1001 FPS, 44100 Hz mono audio; FFprobe verifies its streams. It is synthetic test footage only and is not seeded into the application. The original validation exporter and trim domain model remain unchanged.

Physical OnePlus Pad 2/phone touch, playback/A/V sync, thermal performance, export hardware, OEM document providers, full-file VFR characterization, device signing/update installation and large-font/window-resize behavior remain unverified unless separately documented by an actual device run. Emulator success does not establish these results. Source URI changes still need reselection; full relinking/recovery, multitrack, 4K60 export and M2 editing are not implemented.
